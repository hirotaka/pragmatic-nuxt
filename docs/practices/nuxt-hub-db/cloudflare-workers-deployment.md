# Deploy Nuxt Applications with Cloudflare Workers Builds

## Practice

Use Cloudflare Workers Builds to deploy a Nuxt application directly from its GitHub repository. Connect the repository, set the application root directory and build commands, choose the Production branch, and let Cloudflare manage the build and deployment execution instead of adding a separate GitHub Actions deployment workflow.

Production branch pushes can deploy the Worker, while non-production branch pushes can create Preview versions and Preview URLs.

Configure a Production release command and a Preview release command in Workers Builds. Each command applies the target D1 migration using the Wrangler configuration generated by NuxtHub in that build, then deploys the Production Worker or uploads the Preview Worker version.

Workers Builds does not automatically apply D1 migrations, so include this migration step explicitly in each release command.

## Release Flow for Each Push

1. Push a change to GitHub.
2. Workers Builds builds the Nuxt application for the target branch.
3. NuxtHub generates the Wrangler configuration for the target environment.
4. The release command applies the target D1 migration using the generated configuration.
5. The Production branch deploys the Worker.
6. A non-production branch uploads a Worker version and creates a Preview URL.

## Apply When

- A Nuxt application uses Nitro's Cloudflare Workers runtime and a D1 binding.
- A Nuxt application should deploy from GitHub without a separate repository-owned Cloudflare deployment workflow.
- Production and branch Preview deployments should be managed by one Cloudflare-connected build configuration.
- Production and Preview should resolve different D1 resources when the application uses D1.

## Use Another Practice When

- Local Worker and D1 binding behavior is the concern. Use the Cloudflare Local D1 emulation Practice.
- Fresh hosted SQLite migration and browser verification is the concern. Use the Hosted CI database lifecycle Practice.

## Why

Cloudflare Workers Builds starts from a GitHub push and runs the Production deployment or creates a branch Preview on Cloudflare. The repository does not need a separate GitHub Actions deployment workflow just to deploy to Cloudflare.

The same connection supports a useful Production／Preview workflow: one Production branch can deploy the Worker, and other branches can produce isolated version URLs for review. A branch Preview does not automatically create or select a Preview D1, so the Preview build must explicitly use a D1 separate from Production.

## Implementation Guidance

### Workers Builds Setup

1. Connect the GitHub repository to Cloudflare Workers Builds.
2. Set the Nuxt application's root directory when working in a monorepo.
3. Select the Production branch.
4. Enable non-production branch builds when branch Previews are useful.
5. Configure the Workers Builds commands:

| Workers Builds setting | Command |
| --- | --- |
| Build command | `pnpm build` |
| Deploy command | `pnpm run deploy:cloudflare` |
| Non-production branch deploy command | `pnpm run deploy:cloudflare:preview` |

## Minimal Nuxt Example

```json
{
  "scripts": {
    "build": "bash -lc 'if [[ -z \"${WORKERS_CI_BRANCH:-}\" || \"$WORKERS_CI_BRANCH\" == \"main-worker\" ]]; then pnpm run build:production; else pnpm run build:preview; fi'",
    "build:production": "NITRO_PRESET=cloudflare_module nuxt build",
    "build:preview": "NITRO_PRESET=cloudflare_module CLOUDFLARE_ENV=preview nuxt build --envName preview",
    "deploy:cloudflare": "pnpm exec wrangler --cwd .output/server d1 migrations apply DB --remote && pnpm exec wrangler --cwd .output deploy --keep-vars",
    "deploy:cloudflare:preview": "pnpm exec wrangler --cwd .output/server d1 migrations apply DB --remote && pnpm exec wrangler --cwd .output versions upload"
  }
}
```

The `build` script selects the Production build for the configured Production branch and the Preview build for other Workers Builds branches. The release scripts use the Wrangler configuration generated in the same `.output` artifact. Because the migration and release commands are joined with `&&`, a failed D1 migration prevents the deploy or version upload command from running.

Disable NuxtHub build-time migration for the Cloudflare D1 path so the release scripts apply the committed migration authority at release time.

## Verified App Examples

- [`package.json`](../../../apps/bulletproof-nuxt/package.json) exposes the branch-aware build, Production／Preview build, and migration-aware deploy／version-upload scripts used by Workers Builds.
- [`nuxt.config.ts`](../../../apps/bulletproof-nuxt/nuxt.config.ts) selects different D1 resources for Production and Preview and disables build-time migration for the Cloudflare D1 path.
- [`wrangler.toml`](../../../apps/bulletproof-nuxt/wrangler.toml) keeps the Workers source configuration while NuxtHub generates the resolved D1 binding and migration metadata.
- [`server/db/migrations/sqlite/`](../../../apps/bulletproof-nuxt/server/db/migrations/sqlite/) contains the committed SQLite migrations applied by the release scripts.

## Trade-offs and Limitations

Using one Preview D1 for all non-production branches keeps the Workers Builds configuration small, but it does not isolate schema or data between branch Previews. Concurrent Preview releases can apply migrations to the same database and affect other Preview versions. Use separate Preview databases or serialize releases when branch-level isolation is required.

Applying a D1 migration before releasing the Worker prevents a release when the migration fails, but the migration and Worker release are not atomic. If the migration succeeds and the Worker release fails, the database schema may be ahead of the deployed Worker. Worker rollback does not reverse an applied D1 migration, so migrations should remain compatible with the previously deployed Worker during rollout.

The release scripts depend on the Wrangler configuration and directory layout generated in the Nuxt build output. Reverify these commands when upgrading NuxtHub, Nitro, or Wrangler.
