# Design API Responses for Direct Use with Nuxt Data Fetching

## Practice

For an app-owned internal API[^app-owned-internal-api], design the HTTP response body so the calling code can use the value directly through Nuxt's `useFetch` composable or the ofetch-based `$fetch` function.

The calling code should not need to remove an extra object layer such as `{ data: response }`, use the Nuxt `useFetch` `transform` option to rewrite the body, or supply a TypeScript response type such as `useFetch<ExpectedResponse>()` to make the value appear different from the actual HTTP response. The route should return the same body shape that its calling code expects.

Return a single resource as an object and a collection without metadata as an array. Keep an object such as `{ data, meta }` when pagination details such as the page and total count, or other metadata used by the calling code, are part of the result. When the calling code needs only success or failure and does not use returned data, send no response body and await the operation as `void`, meaning that it produces no result value.

For failures created by the application, throw Nuxt's `createError` so `$fetch` rejects and the app's configured fetch client receives the error. Create that client with ofetch's `$fetch.create()` client factory and handle common failures with an ofetch error-response hook such as `onResponseError`. Do not convert a failure into a successful `{ data, error }` value or wrap every error in another client-defined object.

## Apply When

- Designing a Nitro server route and the Nuxt page, composable, or action that calls it.
- Returning page-rendering data through Nuxt's `useFetch` composable and its `AsyncData` result, which contains Vue reactive refs for data, error, and request status.
- Returning a `useFetch` or project-defined `useAPI` result unchanged from a composable dedicated to one application feature. Here, `useAPI` means a project-defined composable that applies application defaults and delegates the request to Nuxt's `useFetch`.
- Calling an application operation through `$fetch` or an app-defined client such as `$api`, created with `$fetch.create()`.
- Choosing between a resource object, a collection array, an object with metadata, or an operation with no returned data.
- Updating both the server route and its calling code when the response format changes.
- Preserving `createError` failures as rejected fetch requests.
- Using the TypeScript response types generated by Nitro from app-owned server routes.

## Do Not Apply When

- An external or versioned public API has a separately managed compatibility policy.
- A Nuxt module or another external dependency, such as Nuxt Auth Utils, owns the response format.
- The task is to define detailed HTTP status rules, error fields, validation details, authentication, authorization, or resource visibility.
- A third-party response needs adapter code that converts its response body into the shape expected by the application.
- The route returns a stream, file, redirect, or another non-JSON response.

## Why

Nitro is Nuxt's server engine. It serializes the value returned by a server handler as the HTTP response body. Nuxt's `$fetch` function returns that body directly. Nuxt's `useFetch` composable places the same body in the `data` ref of its `AsyncData` result.

The `data` property in `AsyncData` is only the container used by `useFetch`; it does not mean that the HTTP response also needs a `{ data }` object. Designing the route for direct use keeps the actual HTTP body, the JavaScript value available at runtime, and Nitro's generated TypeScript response type aligned.

If a route adds an object layer or a generic success message that its caller does not need, every caller must remove or reinterpret it. Using `transform` or a manually supplied TypeScript type to hide that mismatch creates a second description of the response without changing the value received at runtime.

Converting failures into successful data causes a similar mismatch. It bypasses the configured fetch client's rejection, notification, retry, and cancellation behavior and forces each caller to detect the failure again.

Designing the route and its calling code together keeps Nuxt data fetching straightforward. Related practices continue to own request configuration, pagination mechanics, workflow outcomes, and error notifications.

## Implementation Guidance

- List the value returned by the route and every page, composable, or action that currently uses it before choosing the response body.
- Return a JSON-safe serialized resource object directly when the calling code needs one resource.
- Return a JSON-safe serialized array directly when the calling code needs a collection without metadata.
- Keep an object such as `{ data, meta }` when pagination or other metadata is part of what the calling code needs.
- Return no body when the calling code uses only success or failure. Await the `$api` call without creating a client-only success object.
- Use Nitro's generated response type for app-owned routes instead of supplying a TypeScript response type at the call site.
- Give the `AsyncData` binding a domain name such as `project` or `users`; do not infer an HTTP `{ data }` object from the `data` ref provided by `useFetch`.
- A composable dedicated to one application feature that only chooses an endpoint and options should return the configured `useFetch` or project-defined `useAPI` result unchanged.
- Keep `createError` failures on the rejected fetch path instead of returning them as successful data.
- Preserve the notification, retry, and cancellation behavior already defined by the configured fetch client.
- If a component derives a display-specific error value, keep that value separate from the original fetch error.
- Define detailed HTTP status rules and error response fields in a separate Nitro or server API practice.
- Do not use the Nuxt `useFetch` `transform` option to pretend that the route returned a different body.
- A calling component may select fields or convert values for local use when necessary, but that new value and type should remain separate from the response type generated by Nitro.
- Preserve response formats owned by Nuxt modules or other external dependencies unless the integration explicitly requires adapter code that converts the response body.

## Minimal Nuxt Example

```ts
// server/api/projects/[id].get.ts
export default defineEventHandler(async (event) => {
  const project = await projectRepository.findById(getRouterParam(event, "id"));

  if (!project) {
    throw createError({
      statusCode: 404,
      statusMessage: "Project not found",
    });
  }

  return serializeProject(project);
});
```

```ts
// useAPI applies this app's defaults and delegates to Nuxt useFetch.
// The direct route body becomes a Vue Ref<Project | undefined> in AsyncData.
const { data: project } = await useAPI(
  () => `/api/projects/${projectId.value}`,
);
```

```ts
// server/api/users.get.ts
export default defineEventHandler(async (event) => {
  const users = await userRepository.findAll(event);

  return users.map(serializeUser);
});
```

```ts
// The direct collection body becomes a Vue Ref<User[] | undefined>.
const { data: users } = await useAPI("/api/users");
```

```ts
// server/api/projects/index.get.ts
export default defineEventHandler(async (event) => {
  const page = await projectRepository.findPage(event);

  return {
    data: page.data.map(serializeProject),
    meta: page.meta,
  };
});
```

```ts
// Pagination metadata remains part of Nitro's inferred response type.
const { data: projectsPage } = await useAPI("/api/projects", {
  query: { page, limit },
});
```

```ts
// server/api/projects/index.post.ts
export default defineEventHandler(async (event) => {
  const input = await readValidatedBody(event, projectSchema.parse);
  await projectRepository.create(input);
  setResponseStatus(event, 201);
});
```

```ts
// $api is this app's client created with $fetch.create().
// The calling code needs only success or failure, so there is no result value.
await $api("/api/projects", {
  method: "POST",
  body: input,
});
```

## Verified App Examples

- Discussion detail returns one serialized `Discussion` object. The `useDiscussion` feature composable exposes that object through Nuxt `AsyncData` without using `transform` or supplying a response type manually.
- The Users route returns a serialized `User` array. The `useUsers` feature composable exposes that array without adding or removing an object layer.
- Discussion and Comment routes retain `{ data, meta }`. Their calling composables pass the complete object to the shared pagination logic.
- Actions that need only completion await the app-defined `$api` client as `void` and do not create a client-only success value.
- Failures created with `createError` remain rejected fetch requests and reach the hooks on the configured fetch client.
- Nuxt Auth Utils owns its session response format, so the application fetch layer does not reshape it.

## Trade-offs and Limitations

Designing an app-owned route for direct use means that its calling page, composable, or action depends on the route's actual response body. That dependency is intentional when both sides belong to the same application, and Nitro's generated response types make it visible. External or independently versioned APIs may instead need adapter code that converts their response bodies into the shapes expected by the application.

Different operations can return different shapes, so calling code cannot assume that every response uses one common object such as `{ data, error }`. Those differences are useful when they reflect the value each operation actually returns.

This practice does not define detailed HTTP status rules, validation fields, authorization policy, or the domain fields included in a resource. Evaluate those server API decisions separately while keeping the resulting body straightforward for Nuxt data-fetching callers.

Preserving rejected fetch errors means calling code depends on the error behavior of the configured fetch client. If a component needs a simpler message or another display-specific value, derive it locally without replacing the original fetch error.

[^app-owned-internal-api]: An internal API whose Nitro server route and calling page, composable, or action are maintained by the same Nuxt application.
